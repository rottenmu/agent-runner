# 仓库协作与验证提速设计

## 1. 背景

当前仓库的 Vibe Coding 速度主要受以下流程性因素影响：

- 大小任务都容易进入设计文档、实施计划、用户确认和多轮提交；
- 子代理按微小步骤串行执行，重复读取上下文和等待测试；
- RED、GREEN、模块回归、完整 Reactor 和主应用打包之间存在重复验证；
- 当前工作区有大量既有未提交改动，重复输出全量 `git status` 增加检查和沟通成本；
- Windows split writable roots 环境下，`apply_patch` 更新文件可能失败，重复重试会产生无效等待；
- 完整构建可能被无关模块或文件锁阻塞，但失败发生在流程末端。

本次只优化仓库协作规则和验证策略，不整理、暂存、提交或删除现有工作区改动，不修改 Maven、npm 和沙箱配置。

## 2. 目标

- 根据任务风险选择匹配的设计、计划和审核流程。
- 减少小任务不必要的文档和用户确认轮次。
- 减少子代理启动、上下文加载和串行等待。
- 保留 TDD 的 RED、GREEN 证据，同时避免重复运行大范围测试。
- 把完整验证集中到真正需要的最终阶段。
- 降低脏工作区对日常检查和输出的影响。
- 为 Windows 沙箱写入失败规定直接、可审计的回退方式。
- 保持数据库、安全、代码注释、代码行数和模块边界等质量规则不变。

## 3. 方案选择

### 3.1 采用方案

采用“入口摘要 + 独立详细规则”：

- 在根目录 `AGENTS.md` 增加简短的协作提速摘要和规则文档链接；
- 新增 `docs/rules/AGENT_WORKFLOW_RULES.md`，承载任务分级、执行方式、验证矩阵和异常回退规则；
- 不增加 PowerShell、Maven 或 npm 脚本。

该方案保持 `AGENTS.md` 作为稳定入口，同时让详细策略可以独立维护。

### 3.2 未采用方案

#### 所有规则直接写入 `AGENTS.md`

入口文件会持续变长，项目概览、安全规则和执行细节混杂，不利于快速阅读。

#### 新增快速验证脚本

脚本可以统一命令，但会增加平台兼容、参数组合和脚本维护成本。当前瓶颈首先是验证范围和执行时机，而不是命令输入。

## 4. 任务分级

### 4.1 快速任务

适用范围：

- 只读问答、代码分析、状态检查和故障诊断；
- 文案、注释或配置说明调整；
- 单文件、低风险、行为边界清晰的小改动；
- 不改变公共接口、数据库结构、模块依赖或运行时路由。

流程：

1. 读取目标文件和局部上下文；
2. 必要时在对话中说明假设；
3. 直接执行或给出诊断结论；
4. 运行最窄范围验证。

快速任务不强制：

- 新建设计文档；
- 新建实施计划文档；
- 为文档单独提交；
- 启动子代理；
- 运行模块或全仓完整验证。

### 4.2 标准任务

适用范围：

- 单模块功能；
- 少量紧密关联文件；
- 不改变跨模块公共契约；
- 不增加数据库结构；
- 回滚范围清晰。

流程：

1. 在对话中给出简短设计；
2. 用户确认设计；
3. 在当前会话内按 TDD 实现；
4. 运行具体测试和单模块回归；
5. 必要时进行一次最终代码审查。

标准任务默认不创建独立设计文档和实施计划。用户明确要求文档时除外。

### 4.3 严格任务

适用范围：

- 跨模块公共接口或运行时契约；
- 架构调整或大规模迁移；
- 数据库新增表、字段或迁移；
- Maven 模块依赖、自动配置或应用装配变化；
- 涉及权限、安全、敏感信息或不可逆数据操作；
- 多个独立子系统组成的功能。

流程：

1. 探索上下文并确认需求；
2. 编写中文设计文档；
3. 用户审核设计文档；
4. 编写中文实施计划；
5. 用户选择执行方式；
6. 按 TDD 分阶段实现；
7. 执行受影响范围回归和最终代码审查。

严格任务继续遵守现有“先文档、审核后实施”要求。

## 5. 执行方式

### 5.1 默认当前会话执行

快速任务和标准任务默认由当前会话连续完成，减少以下开销：

- 子代理启动；
- 重复读取技能、规范和计划；
- 任务交接和进度轮询；
- 子代理与主代理之间的范围复核。

### 5.2 使用子代理的条件

满足以下任一条件时可以使用子代理：

- 用户明确要求子代理或并行执行；
- 存在两个及以上互不修改相同文件的独立任务；
- 跨模块工作可以并行验证；
- 需要独立只读代码审查；
- 单个任务耗时较长，主代理可同时完成其他有价值工作。

禁止：

- 为同一方法的测试和实现分别启动代理；
- 为 RED、GREEN、格式检查分别启动代理；
- 在共享文件存在写入冲突时并行代理；
- 仅为满足形式而创建微小子任务。

同一业务单元的 RED、GREEN、重构和局部回归由同一执行者完成。

## 6. TDD 与验证分层

### 6.1 开发阶段

每个行为变化继续遵守：

1. 编写失败测试；
2. 运行该测试并确认因缺失行为失败；
3. 编写最小实现；
4. 重跑同一测试确认通过；
5. 完成必要重构。

开发阶段只运行：

- 指定后端测试类或测试方法；
- 指定前端测试文件；
- 与当前行为直接相关的静态检查。

开发阶段不重复运行完整 Reactor 或生产构建。

### 6.2 业务单元完成

单个业务单元完成后：

- 后端运行所属模块测试一次；
- 前端运行所属插件模块测试一次；
- 同一模块内的多个连续任务合并为一次模块回归。

### 6.3 最终验证

根据改动范围选择：

| 改动类型 | 最终验证 |
| --- | --- |
| 只读分析、文档 | 不运行代码测试 |
| 单个后端类或局部 Service/Controller | 指定测试 + 所属模块测试 |
| 单个前端页面、API 或组件 | 指定测试 + 前端插件测试 |
| 前端路由、依赖、构建配置、生产页面 | 前端插件测试 + `npm run build` |
| starter、公共接口、跨模块契约 | 受影响 Maven Reactor 测试一次 |
| Maven 依赖、自动配置、应用装配 | 受影响 Reactor + `admin-shell package` |
| 发布、CI 或用户明确要求 | `mvn clean verify` |

默认使用增量构建，不主动执行 `clean`。

### 6.4 失败处理

大范围验证失败时：

1. 读取首个真实失败；
2. 判断是否属于本次改动范围；
3. 使用最小命令复现失败；
4. 修复后先运行最小命令；
5. 最终只重跑一次必要的大范围验证。

禁止在没有新证据或新修改时重复运行相同的完整 Reactor。

如果失败来自无关模块、文件锁或环境：

- 不扩大范围修改；
- 记录已通过的相关验证；
- 明确标注未完成的验证和阻塞原因；
- 不把“相关模块通过”描述成“全仓通过”。

## 7. Git 与脏工作区

任务开始时：

- 统计一次工作区修改、删除和未跟踪条目数量；
- 识别目标文件是否已经有未提交改动；
- 不自动清理、暂存、提交或回退既有内容。

任务执行中：

- 使用目标路径限定 `git diff`、`git status` 和 `git diff --check`；
- 不反复输出完整 `git status`；
- 不因全局脏工作区阻止局部、安全的实现；
- 修改前后关注目标文件是否混入无关变化。

只有以下情况才重新读取全局状态：

- 准备提交；
- 发现目标文件被并发修改；
- 用户要求查看完整状态；
- 最终范围审查需要。

## 8. Windows 文件写入回退

本仓库仍优先使用 `apply_patch`。

当 `apply_patch` 因 Windows split writable roots 沙箱失败时：

1. 确认失败来自沙箱准备，而不是补丁上下文错误；
2. 最多重试一次；
3. 再次失败后，使用 PowerShell 和 .NET 对明确目标文件执行 UTF-8 无 BOM 的精确文本替换；
4. 替换前验证旧文本唯一存在；
5. 替换后运行目标文件 diff 和 `git diff --check`；
6. 不使用模糊全局替换或跨目录批量写入。

如果失败来自补丁上下文不匹配，应重新读取文件并修正补丁，不使用回退方式绕过上下文检查。

## 9. 进度沟通

- 工具任务开始前说明目标和验证范围。
- 长时间任务每 60 秒内提供一次有新信息的进度更新。
- 不重复发送“仍在运行”且没有新增证据的状态。
- 子代理等待期间优先完成只读审查、范围检查或准备后续验证。
- 最终回复只汇总结果、验证和真实阻塞，不重复完整过程日志。

## 10. 保持不变的质量规则

以下规则不因提速而降低：

- MySQL 是唯一允许的数据库；
- 敏感信息不得写入日志、文档或聊天回复；
- 后端 Java 中文注释规范；
- 代码行数与拆分规范；
- Controller 和 Service Bean 的唯一 public 构造器注入；
- 插件模块边界和自动配置边界；
- 破坏性操作必须确认目标和授权；
- 不编辑 `target/`、`dist/` 等生成产物；
- 功能和修复仍须先有失败测试。

## 11. 文件变更

本次实施只允许修改：

- `AGENTS.md`

本次实施只允许新增：

- `docs/rules/AGENT_WORKFLOW_RULES.md`

不允许：

- 修改业务代码；
- 修改 Maven 或 npm 配置；
- 新增验证脚本；
- 整理、暂存或提交当前工作区既有业务改动；
- 修改本次规则文件以外的现有文件。

## 12. 验证

规则文档实施后执行：

```text
git diff --check -- AGENTS.md docs/rules/AGENT_WORKFLOW_RULES.md
```

并人工核对：

- `AGENTS.md` 仍保持简短；
- 任务分级没有互相重叠或矛盾；
- 验证矩阵覆盖后端、前端、跨模块和发布场景；
- 快速路径没有绕过安全、数据库或 TDD 要求；
- 文档没有要求自动处理当前工作区改动。
