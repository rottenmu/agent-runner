# 代码行数与拆分规范

本文定义本仓库后端 Java、前端 Vue/JS/TS 代码生成和修改时必须遵守的行数控制规则。核心目标是保持单一职责、方法精简、文件边界清晰，避免超大文件、超长方法和难以维护的堆叠逻辑。

## 一、后端 Java 代码行数规范

### 1. 核心原则

- 遵循单一职责，类、方法、工具能力只承担清晰边界内的职责。
- 方法保持精简，业务流程清晰可读。
- 禁止生成超大长方法，禁止把复杂业务逻辑堆砌在一个方法内。
- Codex 生成代码时，一旦预判超出本规范限制，必须主动拆分、重构和抽离公共逻辑。

### 2. 方法行数上限

所有业务方法、工具方法、查询方法，单个方法有效代码行数最大不超过 `80` 行。

有效代码行统计时，不包含：

- 空行。
- 纯注释行。
- 单独的大括号行。

超过 `80` 行时，必须自动拆分，优先采用：

- 抽取私有方法。
- 抽取通用工具。
- 抽取公共逻辑。
- 抽取策略方法。

禁止通过压缩代码、合并多条语句到一行等方式规避行数限制。

### 3. 各类文件行数上限

| 文件类型 | 单文件有效代码上限 | 超出后的处理方式 |
| --- | ---: | --- |
| Controller 控制器 | `400` 行 | 拆分模块、拆分二级控制器 |
| Service 接口 / ServiceImpl | `500` 行 | 拆分多个 Service、拆分业务模块 |
| Mapper 接口 | `200` 行 | 按业务场景拆分 Mapper |
| 实体类 DO / VO / DTO | 无硬性上限 | 字段过多时按业务维度拆分实体，禁止万能大实体 |
| 工具类 Util | `300` 行 | 按场景拆分，例如金额、日期、字符串、加密分开 |
| 常量类 / 枚举类 | `200` 行 | 多业务常量强制拆分为独立常量类 |

### 4. 特殊行数约束

- `if/else`、`for`、`while` 内部逻辑超过 `30` 行时，必须抽取方法。
- 禁止出现 `3` 层及以上 `if` 嵌套，深层嵌套必须拆分子方法或改为提前返回、策略分发。
- 事务方法只负责流程调度，具体执行逻辑必须拆分到私有子方法或独立服务。
- 禁止超长 SQL 堆在 Java 字符串中；复杂 SQL 应使用 Mapper XML、查询构造器或明确的数据访问方法承载。
- 禁止超长参数校验逻辑堆在业务方法中，通用校验应抽取到校验工具、校验器或独立私有方法。

## 二、前端 Vue/JS/TS 代码行数规范

### 1. 核心原则

- 页面拆分、组件拆分、逻辑抽离、脚本轻量化。
- 页面文件只保留 UI 编排和流程调度，复杂业务逻辑抽离到 hooks、utils、api 或子组件。
- 禁止巨型页面、巨型组件、巨型方法。
- Codex 生成前端代码时，一旦预判超出本规范限制，必须主动拆分。

### 2. Vue 单文件组件行数约束

| 文件类型 | 单文件有效代码上限 | 超出后的处理方式 |
| --- | ---: | --- |
| 页面级 `.vue` 文件 | `500` 行 | 拆分子组件、抽离 hooks |
| 公共组件 | `300` 行 | 按功能拆分多个组件 |
| 弹窗组件 | `200` 行 | 每个弹窗独立组件，多弹窗禁止写在同一个 `.vue` 文件内 |

### 3. JS/TS 工具、接口、Hooks 行数约束

| 文件类型 | 单文件有效代码上限 | 超出后的处理方式 |
| --- | ---: | --- |
| API 接口文件 | `300` 行 | 按业务模块拆分 API 文件 |
| Utils 工具文件 | `200` 行 | 按职责拆分，例如日期、正则、文件、金额分离 |
| Hooks 公共逻辑 | `150` 行 | 复杂业务拆分多个 hook |

### 4. 前端方法行数约束

- 单个 `function`、组合式函数内部局部方法、事件处理方法的有效代码行数最大不超过 `50` 行。
- 表单校验、列表渲染、弹窗逻辑、请求回调禁止堆砌超长代码。
- 复杂业务逻辑必须抽离到 hooks 或 utils。
- 页面层只保留 UI 状态、事件调度和必要的数据装配。

## 三、前后端通用规则

### 1. 有效代码行统计口径

有效代码行指剔除以下内容后的代码行：

- 空行。
- 纯注释行。
- 单独的大括号行。

### 2. AI 生成强制规则

- Codex 生成代码时，一旦预判会超出行数限制，必须主动拆分、重构、抽离通用方法。
- 禁止生成已知违规的超长方法或超大文件。
- 禁止为了控行而破坏语义完整性，拆分后的代码必须保持可读、结构清晰、易维护。
- 禁止通过压缩格式、减少换行、合并语句来规避行数统计。

### 3. 四层拆分原则

所有超长代码优先按以下顺序处理：

1. 拆方法：把清晰的业务步骤抽为私有方法或局部 helper。
2. 拆文件：把不同业务场景拆到独立文件。
3. 抽工具：把通用计算、格式化、校验逻辑抽到工具类或 utils。
4. 抽公共逻辑：把跨模块复用能力沉淀到公共服务、hooks 或框架能力中。

### 4. 最终交付检查

交付代码前必须确认：

- 单方法有效代码未超过对应上限。
- 单文件有效代码未超过对应类型上限。
- 复杂循环、条件分支已拆分。
- 未出现 `3` 层及以上 `if` 嵌套。
- 事务方法只做流程调度。
- 页面组件没有堆叠多个弹窗或多个业务域。
- API、utils、hooks 按业务或职责拆分。
- 拆分后命名清晰，调用链可读，没有为了控行而制造碎片化。
