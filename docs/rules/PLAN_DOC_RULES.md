# 方案与计划文档规范

本文定义本仓库「方案 / 架构决策 / 实施计划 / 较大改动」类文档的存放位置、章节结构与判定标准。适用于 `docs/plans/`、`docs/refactor/` 下的所有计划类 `.md`，以及任何「动手前必须先落地评审」的改动说明。

本规范的章节骨架参考自参考项目 `pi-gui` 的 `plans/*/plan.md`。它的价值不在排版，而在把「凭感觉的乐观」压缩成两样东西：**可被真机判定的事实**，和**被明确写出来的未知**。

---

## 一、存放位置与命名

| 类型 | 位置 | 命名 |
| --- | --- | --- |
| 方案 / 架构决策 / 实施计划 | `docs/plans/` | `YYYY-MM-DD-<topic>.md` |
| 纯重构（不改变对外行为） | `docs/refactor/` | `YYYY-MM-DD-<topic>.md` |
| 骨架模板 | `docs/plans/TEMPLATE.md` | 固定名，不参与命名规则 |

- `<topic>` 使用 kebab-case 英文小写，例如 `trace-virtual-scroll`、`module-agent-memory`。
- 日期取**起草日**，不是完成日；方案跨天迭代时不改文件名，改文档内的「修订记录」。
- 一个方案一个文件。禁止把多个不相关改动塞进同一份文档，也禁止把同一个方案拆成多份互相引用的文档。
- 文档正文默认使用中文（与仓库既有约定一致）。

---

## 二、章节定义

按下面的顺序组织。标「必填」的章节即使内容为空也要保留标题并写明「无」，以此强制回答该问题。

| 章节 | 必填 | 作用 |
| --- | :---: | --- |
| 标题 + 元信息 | 是 | 一句话说明改什么；`状态`（草稿 / 待评审 / 已确认 / 实施中 / 已落地）、`起草日`、`关联模块` |
| 一、置信度与剩余风险 | 是 | 一个百分比 + 最让你睡不着的那条风险 |
| 二、目标 | 是 | 本次要达成什么、明确不做什么 |
| 三、成功标准 | 是 | 逐条列出**真机可判定**的完成条件（见第三节硬性要求 1） |
| 四、参照行为（对标） | 视情况 | 若对标某个成熟产品/项目，逐条列出「要复刻的行为」，而不是抄它的实现 |
| 五、现状差距 | 是 | 现在缺什么、为什么会缺；区分「能力缺失」与「只是没接线」 |
| 六、技术方向 | 是 | 每个方向给出职责边界、关键接口/数据结构、取舍理由 |
| 七、里程碑 | 视情况 | 可独立验证的批次，`M1 / M2 / …`，每批次必须有可观察的产出 |
| 八、自测计划 | 是 | 可照着敲的逐步清单，含预期观察值（见硬性要求 3） |
| 九、已知延后项 | 是 | 明确本期不做的事，写清延后原因，避免被当成遗漏 |
| 十、实施顺序 | 视情况 | 最短路径的执行次序 |
| 十一、实施记录 | 实施后必填 | 实际做了什么、与方案的偏差、偏差原因（见硬性要求 4） |

---

## 三、硬性要求

### 1. 成功标准必须「真机可判定」

每条成功标准都要能被一次真机操作直接判真伪，并且判定结果不依赖主观感受。

| 反例（禁止） | 正例 |
| --- | --- |
| 体验更流畅 | 滚动到底后再追加 200 条消息，连续滚动 5 秒不掉帧，长任务无 > 50ms 的阻塞 |
| 性能更好 | 总条数 500 时，DOM 中 `.msg` 节点数 ≤ 40，且与实际总条数无关 |
| 代码更清晰 | （这类目标不进成功标准，属于技术方向） |
| 功能已实现 | 点 Start → 弹出审批弹窗且 `tool=write_file` → 点批准 → 状态变为 DONE 且步数 `4/4` |
| 修复了卡顿 bug | 输入无匹配关键字时树节点数为 0 且出现 `no session matched` |

判定标准写法要求：

- 有**动作**（点了什么、输入了什么）、有**可读的观察量**（元素数量、状态值、尺寸、状态码），不是"看起来对不对"。
- 涉及时间/尺寸的，给出阈值（如 `≤ 40`、`> 0`、`< 50ms`），不要写"较小""明显"。
- 「代码写完」「编译通过」「单测通过」**不算**成功标准，它们只是前置条件。

### 2. 置信度必须搭配风险

`一、置信度与剩余风险` 只写两行：

```markdown
- 当前置信度：92%
- 主要剩余风险：<一句话说清最可能翻车的地方，以及它会以什么形式暴露>
```

置信度是对「方案能否按预期落地」的估计，不是对「代码能不能写出来」的估计。低于 70% 的方案不应进入执行阶段，应先补验证性实验并在文档里记录实验结果。

### 3. 自测计划必须是可照做的清单

- 写成**编号步骤**，动词开头，逐步可执行。
- 每步尽量给出**预期观察值**，便于执行时逐条对账，而不是"跑一遍看看"。
- 禁止写"全面测试""充分验证"这类无法执行的要求。
- 若某项验证手段本身有语义缺陷（例如用隐藏窗口测试"窗口聚焦才抑制通知"），必须显式写出该缺陷，并说明「通过 ≠ 正确」。测试不得虚报置信度。

### 4. 实施后必须回填实施记录

文档不是一次性交付物。实施完成后必须回到同一份文件补 `十一、实施记录`，至少写清：

- 实际改动清单（文件 / 模块）。
- **与方案的偏差**及原因。方案与实现不一致却任其腐坏，是文档失去可信度的唯一原因。
- 真机验证的实际结果（可直接贴自测计划的逐条结论）。
- 验证过程中新发现的坑（这类内容往往比方案本身更有长期价值）。

若实施过程中方案发生方向性变化，先改文档再改代码。

## 四、反模式清单

- **把"待办清单"当方案**：只有步骤没有判定标准的文档不满足本规范。
- **只有理想路径**：不写失败分支、回滚方式、兼容性破坏面。
- **过度自信的绝对化表述**：出现「完全兼容」「百分之百」「不会有问题」时，必须补充验证依据。
- **复制粘贴的历史文档**：新方案必须重新回答「现状差距」，不得沿用上一份方案的结论。
- **把敏感信息写进文档**：连接串、密钥、真实账号一律不得出现在计划文档中；用环境变量占位符表示。

## 五、与其他规则的关系

- 本规范只约束**计划类文档**的写法。代码注释规范见 `BACKEND_JAVA_COMMENT_RULES.md`，代码行数规范见 `CODE_SIZE_RULES.md`。
- `AGENTS.md` 已规定：涉及方案、架构、实施计划或较大改动时，**先写文档并等待用户审核确认，再按文档进入执行阶段**。本规范定义的就是那份文档该长什么样。
- 文档确认后若用户直接要求开工，可以直接执行，并在执行完成后回填「实施记录」；执行期间新增的偏差仍需写回文档。
