# 链路可观测性设计说明

> 最后更新：2026-09-13
> 相关配置：`ai.agent.trace-middleware-enabled` / `ai.agent.otel-*`
> 相关代码：`framework/framework-ai/src/main/java/com/zimo/framework/ai/observ/`

## 1. 为什么需要这套东西

改造前，一次 `/api/biz/ai/chat` 调用在「可观测」页只能看到 **3 个步骤**：

```
invoke_agent            (running, 0ms)
intent / 意图路由        (ok,      0ms)
agent_reply             (failed,  2601ms)
```

中间是**一片空白**——agent 内部跑了几轮推理、调了几次模型、每次耗时多少、有没有调工具，
完全看不到。一条 2.6 秒的失败请求，只有首尾两个点，排查时无法定位到底卡在模型调用还是工具执行。

根因是 **ThreadLocal 在响应式线程切换处失效**：

```
HTTP 线程 (nio-9900-exec-N)          Reactor 调度线程 (boundedElastic-N)
────────────────────────────         ─────────────────────────────────────
AiAgentService.executeCore
  TraceCollector.begin()  ─────┐
  CURRENT_TRACE.set(id)        │ ThreadLocal 只在本线程有效
  agent.call(msg).block() ─────┼──→  ⚙ onAgent / onReasoning / onModelCall
                               │      ⚙ TraceCollector.step() 取 CURRENT_TRACE → null
  TraceCollector.end()   ←─────┘      ⇒ 静默丢弃，链路出现空白
```

`agent.call(...).block()` 把 Reactor 流拉回阻塞线程，但模型调用与工具执行**仍然发生在
Reactor 的调度线程上**，那里读不到 HTTP 线程写入的 ThreadLocal。

## 2. 解决方案：双通道互补

| 通道 | 实现 | 产出 | 默认 | 用途 |
|---|---|---|---|---|
| **自研桥接** | `HarnessTraceMiddleware` | 项目自有 trace 步骤（落 `observ_session_event` 表） | **开启** | 前端「可观测」页展示、SQL 可查 |
| **标准 OTel** | `OtelTracingMiddleware` | 标准 OTLP span 树 | 关闭 | 导出到 Jaeger / Langfuse 等 |

两者**不是二选一**：一个解决「项目自己的链路页面没内容」，一个解决「要接外部 APM」。
可同时挂载，互不干扰。

### 2.1 自研桥接：跨线程传 traceId

关键手段是把 traceId 放进 **`RuntimeContext` 的 key-value 区**，而不是 ThreadLocal。
`RuntimeContext` 在整次 reply 内被各层 hook 共享，且**跨线程是同一个实例**（已实测：

```
[nio-9900-exec-7]     ctx=8318311 extra={..., zimo.traceId=e56a9dce5b014f08}
[boundedElastic-1]    ctx=8318311 extra={..., zimo.traceId=e56a9dce5b014f08}
```

同一 `identityHashCode`，`extra` 中 traceId 一致）。

写入点：`AiAgentService` 在 `TraceCollector.begin()` 之后、调用 agent 之前调
`HarnessTraceMiddleware.bindTraceId(context, traceId)`。

> ⚠️ **两条执行路径都要绑**：`executeCoreWithHistory`（`driveRuntime` 走）与
> **`executeCore`**（middleware 链尾，`/api/biz/ai/chat` 实际走这条）。
> 只绑前者会导致线上路径完全无记录——这是改造中踩过最深的坑。

读取点：中间件各 hook 从 `ctx.get("zimo.traceId")` 取回，用 `TraceCollector.stepFor(traceId, ...)`
（**不是** `step()`，后者读 ThreadLocal）跨线程写回。

未绑定时静默降级（不伪造 ID、不影响主流程），并**仅告警一次**（`UNBOUND_WARNED` 标志），
避免高频请求刷日志。

### 2.2 覆盖的 hook

AgentScope 提供 5 个 hook，本中间件用 4 个：

| hook | 类型 | stepType | 记录内容 | order |
|---|---|---|---|---|
| `onAgent` | Onion | `agent` | agent 名、输入消息数、总耗时 | 0 |
| `onReasoning` | Onion | `reasoning` | 本轮 messages / tools 数、耗时 | 0 |
| `onModelCall` | Onion | `model_call` | 模型类名、messages / tools 数、耗时 | 0 |
| `onActing` | Onion | `tool_call` | 工具名列表、耗时 | 0 |
| `onSystemPrompt` | Transformer | — | 未使用（返回 `Mono<String>`，与链路无关） | — |

`order()` 返回 0，让官方 `OtelTracingMiddleware`（默认 `order=1`，数值越大越外层）先建立
span 上下文，本类记录的时间区间落在其 span 内，便于两边对照。

### 2.3 ⚠️ 成功与失败必须成对处理

所有 hook 都同时挂 `doOnComplete` 与 `doOnError`：

```java
return next.apply(input)
        .doOnComplete(() -> TraceCollector.stepFor(traceId, "reasoning", ..., "ok"))
        .doOnError(error -> TraceCollector.stepFor(traceId, "reasoning", ..., "failed"));
```

**只挂 `doOnComplete` 会漏掉所有失败请求的事件**。改造中 `onReasoning` 起初只有成功分支，
现象是「官方 `AgentTraceMiddleware` 打印了 `PRE_REASONING`，证明 hook 被调用，但自研链路里
就是没有 `reasoning` 事件」——因为本次请求以 404 报错终止，`doOnComplete` 永不触发。
补上 `doOnError` 后事件数从 6 → 8，`reasoning` 正常出现。

### 2.4 每个动作只记一条事件

统一采用「完成时记一条」（`ok` 或 `failed`），不在开始时额外记 `running`。
否则一次模型调用会产生 `start` + `ok` 两行，ReAct 多轮下噪音迅速累积。
例外是 `invoke_agent`（由 `AiAgentService` 记录，属外层链路语义，保留 `running` 起点）。

## 3. 标准 OTel 通道

`OtelTracingInitializer` 负责 SDK 初始化，`OtelTracingMiddleware` 产出 span。

初始化要点：

1. **幂等**：`synchronized` + `tracerProvider != null` 短路，重复调用直接返回。
2. **不覆盖外部已配置的全局 provider**：`isGlobalAlreadyConfigured()` 反射查
   `GlobalOpenTelemetry.get().getTracerProvider()` 的类名，含 `DefaultTracerProvider` /
   `NoopTracerProvider` 才算「未配置」。避免与用户自带的 javaagent 冲突。
3. **`OtelTracingMiddleware` 的构造器本身就有副作用**——内部调用
   `ContextPropagationOperator.registerOnEachOperator()` 注册 Reactor 上下文传播 hook
   （由静态 `hookRegistered` 标志保护，幂等）。所以**只要 new 出来就会生效**，
   `order` 与挂载顺序不影响它能否工作。
4. **版本必须与 `agentscope-core` 对齐**：统一走根 POM 的 `opentelemetry-bom`（当前 1.61.0）。
   `opentelemetry-reactor-3.1:2.27.0-alpha` 由 agentscope-core 传递引入，版本不受 BOM 管。
5. **注册 shutdown hook** 保证 `BatchSpanProcessor` 的缓冲 span 在进程退出前 flush。

### 配置项

```yaml
ai:
  agent:
    trace-middleware-enabled: true    # 自研桥接，建议常开（开销极小）
    otel-enabled: false               # 标准 OTel，按需开启
    otel-endpoint: http://localhost:4318/v1/traces
    otel-authorization: ""            # 敏感，优先走环境变量 OTEL_EXPORTER_OTLP_AUTHORIZATION
    otel-service-name: agent-runner
```

`otel-endpoint` 未显式配置时按 `OTEL_EXPORTER_OTLP_ENDPOINT` 环境变量 → 标准默认值的顺序回退。

## 4. 验证

```
POST /api/auth/login        {"username":"admin","password":"admin","department":"行政"}
POST /api/biz/ai/chat       {"agentId":"...","message":"你好","sessionId":"...","userId":"..."}
GET  /api/biz/ai/observ/traces?limit=5
GET  /api/biz/ai/observ/events/{traceKey}
```

> ⚠️ 鉴权头是 **裸 token**：`Authorization: <token>`，**不带 `Bearer ` 前缀**。
> 登录接口是 `/api/auth/login`（不是 `/api/biz/sys/login`），字段名是 `department`（不是 `tenantCode`）。

改造后的实测事件序列（8 条，ReAct 2 轮）：

```
seq=0  —            invoke_agent 工具调用测试     running    0ms
seq=1  intent       意图路由                      ok         0ms
seq=2  model_call   模型调用 DashScopeChatModel   failed   210ms
seq=3  reasoning    推理轮次                      failed   298ms
seq=4  model_call   模型调用 DashScopeChatModel   failed    30ms
seq=5  reasoning    推理轮次                      failed   115ms
seq=6  agent        智能体执行 工具调用测试        failed   681ms
seq=7  —            agent_reply                   failed  1178ms
```

`reasoning` / `model_call` 交替出现即 ReAct 轮次的正确形状。

> 本次验证时 LLM 调用本身返回 `404`（模型名 `qwen3.8-max-preview` 配置问题），
> 因此所有内层步骤都是 `failed`。这只影响状态字段，**不影响链路完整性验证**——
> 反而正好覆盖了失败路径。修复模型配置后状态会转为 `ok`。

## 5. 与项目既有可观测三层的关系

```
HarnessTraceMiddleware ──┐
                         ├──→ TraceCollector ──┬──→ GenAiTraceObserver          (GenAI 风格 span)
AiAgentService(外层 begin)┘                    └──→ SessionEventLogServiceImpl   (observ_session_event 行)
                                                          ↓
                                                   前端「可观测」页 / SQL 查询

OtelTracingMiddleware ─────→ OTLP exporter ─────────→ Jaeger / Langfuse 等

AgentTraceMiddleware（Harness 自带 18 个中间件之一）──→ 仅有 SLF4J 日志，非持久化
```

三套并存不冲突：`AgentTraceMiddleware` 是官方调试用日志，`HarnessTraceMiddleware` 是
项目自有持久化链路，`OtelTracingMiddleware` 是对外标准协议。

## 6. 排查清单

| 症状 | 检查点 |
|---|---|
| 链路里只有 `intent` + `agent_reply` | `trace-middleware-enabled` 是否为 true；`AiAgentService` 是否在**实际执行路径**上调了 `bindTraceId` |
| 日志见 `RuntimeContext 未绑定 zimo.traceId` 告警 | `bindTraceId` 漏调或 `context` 传的是另一个实例 |
| 某类 hook 事件缺失 | 该 hook 是否挂了 `doOnError`；请求是否以异常终止 |
| 事件全部 `failed` 但链路完整 | 正常——查 `model_call` 的 outputJson 里的具体错误 |
| 开启 OTel 后无 span 上报 | `otel-enabled`；endpoint 可达性；是否被 `isGlobalAlreadyConfigured` 短路 |
